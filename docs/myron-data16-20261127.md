# Preserve Data and use the available 16 GiB window

The current device-bound layout has a 32 GiB `unixnu` partition. The signed
root occupies about 14.1 GiB. Keeping the original 1 GiB Data extent and the
carrier/log tail allows a separate **16 GiB** Data extent, with 849.45 MiB left
above the root's 4 MiB guard. A 17 GiB separate extent does not fit. No Android
partition or GPT entry needs to change. This is a geometry result, not a report
that a phone's APFS filesystem has already grown.

The upstream UniXNU seed grower chooses a whole-GiB size after subtracting root,
guard, log reserve, overlay metadata and a spare GiB. Replacing the seed changes
its identity and does not preserve this installation. The Xiaomi 17 Ultra
reference reports a 16-to-64 GiB expansion, but uses an iOS 16 HFSX root file in
Android storage, a different filesystem and allocation scheme. Its coordination
record also documents corruption after booting an older extent table. Do not
copy its HFS volume-header/journal edits into APFS or use an old boot package
after activating our expanded store.

Implemented source paths:

1. `myron-data-grow=16` opts into the copy **before NativeRamBlock publication**.
   The UFS write window covers only the new extent. The core reads current Data
   directly, copies present pages, reads every write back, extends the bitmap,
   checks source metadata again and commits the destination last. A committed
   copy is never replaced on retry. A recognized old experimental 4 GiB copy
   stops migration rather than using stale original Data.
2. RamBlock retains the immutable 1 GiB seed hash, expands only its pointer
   index to 32 MiB, and publishes the selected 16 GiB disk. Store selection,
   mount authorization, exporter and the last-page I/O test use the same size.
   The persistent log now records selected capacity and copy status.
3. `myron-data-grow` is a separate arm64e iOS27 helper. Its default operation is
   inspection. It resolves `/private/var` through the APFS IOKit hierarchy,
   requires a single physical store under NativeRamBlock, checks raw block
   capacity and the APFS superblock checksum, and refuses arbitrary disk paths.
   `--grow` also requires the kernel's committed 16 GiB authorization property.
   It resolves Apple's minimum-size and resize APIs, journals intent before
   calling resize, and validates volume UUID, container identity, capacity and
   free space afterwards. Interrupted/failed calls are not automatically retried.

Host tests exercise actual transformed start/store/mount code, sparse exports,
16 GiB end-of-disk I/O, 34 injected migration I/O failures and retry behavior,
checksum corruption, capacity refusal and one-attempt API policy. They do not
qualify the APFS API on iOS27 or UFS behavior during power loss.

The full-package workflow now selects `MYRON_DATA_GROW=16`. Packaging refuses
this selection without the audited helper and Metal sidecars. On the phone,
the first boot copies the current overlay before publishing its block device;
launchd subsequently attempts APFS growth once, after all runtime guards pass.
The application staging pass runs earlier, so apps may need one further normal
boot after verified growth. There is no automatic reboot or repeated resize.

Read `/private/var/root/myron-data-grow.log` for `expanded-and-verified`, and
correlate it with the kernel's `myron-data-growth` and `myron-data-helper` lines.
`selectedMiB=16384` proves block-device selection only, not APFS free space.
Do not delete the attempt marker or boot an older package to force a retry.
